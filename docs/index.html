Beltline · a skill for Claude Code

Point Claude at a program, and it draws the factory that runs it.

/beltline16 machines60 testsby Vasco9 November 2026Install ↓

Most pictures of how a program works are boxes and arrows. They tell you which parts exist, but not what the data looks like as it passes through them, so the reader has to run the program in their head. I wanted Claude to draw the data moving: one real input, travelling through the real structures, changing the real cells.

Beltline is a skill for Claude Code that does this. You point it at a repository or a subsystem. Claude reads the source, picks a concrete input from the tests, and draws the program as a small factory. Each data structure is a machine shaped like its behaviour, the input rides belts from entry to exit, and every station links to the source line that proves it. The result is one animated SVG that also works as a plain image in a README.

This tour came from one line, /beltline /src/velocitty — the whole terminal, bytes from the pty to pixels, given to a fresh Claude that had never seen the program. It read the Zig source, took its two inputs from the ring buffer's own tests, and traced them through eighteen machines.1

1Nothing was run. Every value comes from reading the code at revision 2d5a1a4, and the tour says so in its subtitle.

Watch the drum on the left. Its tail arm stops behind three bytes of an unfinished escape sequence, and the next read completes them. The colour lands in the pen, the style table interns it as id 1, and the é misses the glyph cache, so it is rasterised into the atlas before it reaches the framebuffer.

Machines, not dashboards 01

The skill rests on one rule, at the top of its instructions:

The machine is the explanation.

SKILL.md, “The one idea”

A reader should know what a structure is from its shape and its motion, before reading its label. A ring buffer is a drum whose arms turn. A stack is a spring tube that fills from the bottom. A tokenizer is a cutter. If a station needs a paragraph next to it, the drawing has failed.

It fails in two ways, and the first version of this skill did both. The dashboard: every station a panel of fields, code and notes, correct but unreadable. Boxes and arrows: identical labelled rectangles, so nothing shows what kind of structure each one is. The fix for both is the same: a fixed catalogue of small machines, and a kit that refuses to place text the reader doesn’t need.2

Writing a prompt 02

The prompt is the scope, not the drawing. Name a repository, a subsystem or one path through it, and Claude decides which machines it needs. A few words change what you get:

just …Narrows the tour to one path or subsystem. Without it, Claude tours the whole program and offers smaller tours of the parts it had to leave out.
as x.svgNames the output file. The default is beltline.svg in the repository, with its build script next to it.
source onlyIgnores existing docs and diagrams completely. Claude reads them anyway only to point out where they disagree with the code.
The whole programthis repo
One pathjust the request path, from the router to the response, as request.svg
One structurehow the LRU in src/cache evicts entries
Without the commandshow me how this parser works, as a picture

You rarely need the command. The skill’s description covers visual codebase tours, data-flow pictures and “show me how this code works”, so Claude reaches for it on its own.3

3It also answers to the old name, factorio.md, so existing prompts keep working.

What Claude does 03

Between your line and the finished SVG, Claude works through a fixed order. Most of the clarity is decided in step three, before anything is drawn.

  1. Size it. One path, one subsystem or the whole plant, each with a ceiling on machines and steps. A whole large program becomes an overview plus smaller tours.
  2. Read and trace. Follow the real calls, mutations and branches, and walk a concrete input from the tests through every step, noting each value before and after.
  3. Cast the machines. Give each store one machine from the catalogue, chosen by behaviour. Functions that only pass data along become belts.
  4. Lay out the floor. The main route on one row, stores under their owners, side paths in their own lanes.
  5. Write the steps. Each step moves one item along a belt or puts one machine to work, with its writes, a one-line caption and its source line.
  6. Build, check and look. Three scripts must reach zero. Then Claude screenshots the frames, opens every one and fixes what a critic would find.

Casting 04

Before any layout, Claude writes a cast table and shows it to you. This is the calculator from the examples, evaluating 2*(3+4):

StructureMachineWhy
tokensrack of 7, with an i pointera contiguous array walked by index
opsspring tubepush and pop are the whole point
outrack of 5postfix order fills left to right
stackspring tubeevaluate pops two and pushes one
tokenize()cutterit cuts one string into pieces

The cast is about behaviour, not type names. A Vec used as a stack is a spring tube. A HashMap used as an LRU gets the eviction chute. A parser is a selector only if its source really keeps a state variable.4

4Each store shows a window of three to eight cells, the ones the trace touches. A 1 MiB buffer is still a rack of six.

The kit 05

Claude never writes SVG by hand. It writes a short build script against the kit, saying what the machines are and where they sit. The kit draws, routes, animates and themes them, and audits the result before it writes a byte.

examples/calc/build.mjs
F.machine("tokenize", { kind: "cutter", at: [6, 2], label: "tokenize()", src: "calc.js:1" })
 .machine("tokens", { kind: "rack", at: [12, 2], label: "tokens[]", src: "calc.js:2",
           cells: ["", "", "", "", "", "", ""], pointers: { i: 0 } })
 .machine("ops", { kind: "stack", at: [24, 7], label: "ops[]", src: "calc.js:24", cells: ["", "", ""] });

F.belt("tokenize", "tokens").belt("toRpn", "ops").belt("ops", "toRpn");

F.step({ belt: "toRpn->ops", item: "*", writes: { ops: [[0, "*"]] },
          pointers: { tokens: { i: 1 } }, caption: "* finds ops[] empty and waits there", src: "calc.js:33" });

The static markup is always the end state: every cell holds its final value and the last caption is showing. Playback starts from the initial values, runs once, and lands exactly there. So a reader with reduced motion, or a README that never plays it, still gets the whole story.5

5All motion lives inside prefers-reduced-motion: no-preference, and colours are tokens with a dark set, so the same file follows the reader’s theme.

Checks that fail closed 06

Each check prints one fixed line when everything is at zero, and exits with an error otherwise. Claude keeps going until all of them pass.

CheckWhat it catchesMust print
The kit’s auditbelts through machines or crossing, text on text, values too wide for their cells, disconnected machines, the clutter budgetaudit passed
check.mjsscripts, remote assets, broken references, motion outside the reduced-motion gate, too many colours, paragraphs on the canvassvg check passed
check-sources.mjsa station or caption pointing at a file or line that doesn’t exist at the recorded revisionsources: 0 unresolved
capture.mjsfreezes the animation at chosen moments and widths; fails if the still view differs from the last framecapture done

A zero audit is necessary, not sufficient. After the scripts pass, Claude opens every screenshot and takes close-ups of each dense junction, looking for what only a person would notice: a shape that doesn’t read as its structure, a route the eye has to hunt for.6

6Every check is tested against a deliberately broken input first. A check that doesn’t fail on its planted fault is treated as broken.

Before and after 07

Install 08

Clone it into your skills folder. The kit and scripts need only Node; the screenshot checks also need Chrome or Chromium.

# Claude Code
git clone https://github.com/valvesky/beltline ~/.claude/skills/beltline

# Codex
git clone https://github.com/valvesky/beltline ~/.codex/skills/beltline

Requirements: Node 20 or newer. Chrome or Chromium for capture.mjs, found on the path or through CHROME_PATH. ImageMagick for contact sheets and the still-view comparison.

Limits 09

  1. It is a walkthrough, not a recording. Values come from reading the source and its tests. Nothing in your project is built or run.
  2. A whole large program does not fit. Past about twenty-four machines, Claude draws an overview and offers a tour per subsystem.
  3. It plays once. An SVG shown as an image has no pause button, so playback holds its end state instead of looping. No scrubbing yet.
  4. Small at phone width. At 390 pixels the shapes and route still read; the values need the full-size file.

Questions 10

Does it run my code?

No. Claude reads source and tests, and runs only the skill’s own kit and checks.

Why one SVG and not a web page?

So it can live in a README, a pull request or docs as a plain image, with no scripts and no hosting. It follows the reader’s light or dark theme on its own.

Can I change the tour afterwards?

Yes. The build script is saved next to the SVG. Move a machine, edit a caption, rebuild, and the checks run again.

What happens when the code changes?

The tour records the revision it read. Run the source check against a newer revision and it lists every station whose line no longer holds up.

Where did the name come from?

It started as factorio.md, after the factory game whose belts inspired the look. Beltline keeps the idea and drops the borrowed name.
